# Kiro CLI Agent Loop 데모 — 대화 및 목표 인수인계

작성일: 2026-10-20 / 발표 예정: 2026-10-21 (수)

## 1. 배경과 목표
- AI Engineer World's Fair 2026에서 언급된 Loop 개념을 개발자 팀원들에게 처음 소개한다.
- 청중은 Loop를 처음 듣는 개발자이며, 쉽게 이해할 수 있는 설명을 우선한다.
- Java 기반의 간단한 실습 프로젝트를 사용하고, AI 도구는 **Kiro CLI**, 실행 환경은 **Mac**으로 확정했다.
- 라이브 코딩은 필수가 아니다. 사전에 직접 실행하고 주요 장면을 캡처해 발표 자료에 넣는다.
- 프로젝트는 사용자가 이미 GitHub에 업로드했다. 이후 작업은 Kiro에서 이어간다.

## 2. 가장 중요한 메시지
일반적인 Claude Code/Kiro 사용도 내부적으로 Agent Loop를 실행한다. 하나의 프롬프트만으로 개발과 테스트, 수정이 모두 끝날 수도 있다.

이번에 보여줄 **외부 자율 Loop(Outer Loop)**의 차이는 다음과 같다.
1. AI 세션이 완료되더라도 외부 Controller가 별도로 검증한다.
2. 검증에 실패하면 **사람이 재지시하지 않아도** 새 Kiro CLI 실행을 시작한다.
3. AI의 '완료' 판단과 시스템의 '완료 승인'을 분리한다.
4. 성공, 최대 반복 횟수 초과, 오류 등의 종료 조건을 Controller가 관리한다.

핵심 문장: **Loop는 새로운 프롬프트 마법이 아니라, AI 작업의 실행·피드백·검증·종료 조건을 설계하는 방식이다.**

## 3. 합의한 데모
- Java 할인 계산 기능(또는 할인 API)을 예제로 사용한다.
- 정상 할인, 할인율 0~100%, 음수 금액 거부, 100% 할인, 경계값 등을 검증한다.
- Kiro CLI가 Java 소스를 분석하고 수정한다.
- 외부 Python Loop Controller가 별도의 Java 테스트/QA Gate를 실행한다.
- 실패 로그를 다음 Kiro 실행에 전달하고 새 세션을 시작한다.
- 모든 검증이 통과하면 종료하고 결과/반복 이력을 기록한다.

예상 흐름:
```
목표/요구사항
    ↓
Outer Loop Controller (Python)
    ↓
Kiro CLI 비대화형 실행 → Java 코드 수정
    ↓
독립적인 QA Gate
    ├─ FAIL → 로그 기록 → 새로운 Kiro 실행
    └─ PASS → 종료/결과 보고
```

**주의:** Kiro가 첫 번째 실행에서 전부 해결하면 1회로 끝나는 것이 정상이다. 2회 이상 반복되는 장면을 강제로 AI 실패처럼 연출하지 말 것. 반복 설명이 필요하면 '의도적인 실패 주입/Mock 시연'이라고 명시한다.

## 4. 프로젝트 및 실행 명령
앞선 대화에서 전달한 프로젝트 이름: `kiro-agent-loop-demo.zip`.
현재 사용자가 해당 프로젝트를 GitHub에 업로드했다고 설명했다. 이 문서는 특정 저장소 URL이나 브랜치를 알지 못하므로 임의로 가정하지 않는다.

Mac 터미널에서 저장소 루트로 이동 후:
```bash
java -version
javac -version
python3 --version
kiro-cli --version
```

초기 상태 확인:
```bash
python3 verify.py
```

Mock으로 Controller 흐름 확인:
```bash
python3 loop.py --provider mock --reset
```

실제 Kiro CLI:
```bash
python3 loop.py --provider kiro --reset --max-iterations 5
```

위 명령과 파일명은 이전에 안내한 데모 프로젝트 기준이다. **현재 GitHub 저장소의 파일 구조와 CLI 옵션을 먼저 확인한 후 실행할 것.** 이 인수인계 문서를 작성하면서 실제 저장소의 최신 내용이나 Kiro 연동은 검증하지 않았다.

### 보안/실행 주의
- 비대화형 Kiro 실행의 권한과 CLI 인자를 로컬 설치 버전에 맞게 확인한다.
- `--trust-all-tools`는 광범위한 권한을 부여할 수 있다. 비밀정보가 없는 실습 저장소에서만 사용하고 가급적 제한된 권한/격리 환경을 쓴다.
- QA Gate가 수정 대상과 같은 쓰기 가능한 폴더에 있으면 AI가 테스트를 변경할 수 있으므로 별도 보호가 필요하다.
- 무한 반복 방지: 최대 반복 횟수, 실행 타임아웃, 실패 처리, 로그 기록을 둔다.

## 5. 캡처해야 할 장면
1. 초기 Java 코드와 누락된 검증 조건
2. 첫 Kiro 실행 및 완료 메시지
3. 외부 QA Gate FAIL 결과
4. 사용자 추가 입력 없이 Controller가 새 Kiro 실행을 시작한 로그
5. QA Gate PASS와 Controller 종료/반복 횟수 요약

가능하다면 터미널에 `[LOOP 1]`, `[QA GATE] FAIL`, `[LOOP 2]`, `[QA GATE] PASS`가 보이게 한다.

## 6. 발표 구성안 (약 30분 + Q&A)
| 시간 | 내용 |
|---|---|
| 0–5분 | Loop가 왜 주목받는지 / 문제 제기 |
| 5–10분 | 기존 대화형 AI, 내부 Agent Loop, 외부 Outer Loop 비교 |
| 10–15분 | Java 데모 목표·검증 기준·아키텍처 |
| 15–23분 | 사전 캡처 기반 Kiro 실행 결과 시연 |
| 23–27분 | QA Gate, 재실행, 종료 조건, 안전장치 |
| 27–30분 | 실무 적용(테스트 자동화/CI), 요약 |
| 이후 | Q&A |

발표에서 피해야 할 주장:
- '기존 Kiro는 반복 작업을 못 한다' (사실이 아님)
- '외부 Loop가 무조건 더 좋은 코드를 만든다' (입증되지 않음)
- 'AI가 항상 2번 이상 반복한다' (쉬운 목표는 1회에 성공할 수 있음)

## 7. Kiro에서 다음으로 할 일
1. 저장소의 README, `loop.py`, `verify.py`, Java 소스와 테스트를 점검한다.
2. Kiro CLI 설치/인증 및 비대화형 호출 구문을 로컬에서 검증한다.
3. Mock → 실제 Kiro 순서로 실행한다.
4. 첫 실행 성공 시에도 설명 가능한 캡처를 확보한다. 필요하면 의도적 Gate 실패를 주입하는 **별도 명시적 데모 모드**를 만든다.
5. 반복별 로그, 최종 보고서, 변경 diff를 캡처한다.
6. 발표 PPT에 실제 실행 결과를 반영한다.
